## 1. 경위 요약

본인은 상기 기간 중 AWS Bedrock의 Claude 계열 모델을 **멀티에이전트 병렬 개발** 방식으로 활용하여
본 프로젝트를 개발하였습니다. 단일 세션에서 순차적으로 작업하는 방식이 아니라, 여러 개의 에이전트를
**동시에 실행**하여 서로 다른 레인(lane)과 트랙(track)을 병렬로 진행하였고, 그 결과 8일간
**164건의 커밋**과 **약 108,921줄의 코드 추가**가 이루어졌습니다.

이 과정에서 발생한 Bedrock API 호출량과 토큰 사용량은 아래와 같으며, 모두 CloudWatch
`AWS/Bedrock` 지표를 직접 조회하여 확인한 **실측치**입니다.

## 2. 멀티에이전트 병렬 개발 경위

### 2.1 병렬 진행 구조

작업은 처음부터 **레인(lane) 단위로 소유권을 분리**하여 설계되었습니다. 이는 여러 에이전트가
동시에 코드를 수정할 때 서로 충돌하지 않도록 하기 위한 조치였습니다.

프로젝트 문서(`infra/README.md`)에 명시된 원칙:

> "Lane A owns all Terraform implementation under `infra/`."
> "A lane task never edits another lane's Terraform or application path."
> (A레인이 `infra/` 하위의 모든 Terraform 구현을 소유한다.
>  하나의 레인 작업은 절대 다른 레인의 Terraform이나 애플리케이션 경로를 수정하지 않는다.)

또한 인프라 루트 자체를 `foundation` / `data-ai` / `application` 3개로 분리하였는데,
이는 자주 배포되는 컴퓨팅 변경이 보존해야 할 데이터 리소스를 건드리지 못하게 하기 위한
병렬 작업 전용 격리 구조입니다.

### 2.2 트랙별 병렬 분담

`docs/specs/` 하위에 트랙별 명세를 두고 4개 트랙을 동시에 진행하였습니다.
각 명세에는 **"다른 트랙과의 겹침"** 절이 별도로 존재하며, 이는 병렬 실행 시의
충돌 지점을 사전에 문서화한 것입니다.

| 트랙 | 담당 범위 |
| --- | --- |
| Track 1 | GCP 인지 계층 (cognitive layer) |
| Track 2 | 채점 및 리뷰 (scoring and review) |
| Track 3 | 면접 진행 화면 및 접근 제어 |
| Track 4 | 신원 확인 및 정원 관리 |

Track 2의 인계 문서에는 브랜치 `feature/scoring-arithmetic`, 기준 커밋
`84af2d4`, 그리고 **2026년 8월 20일 pytest 206건 통과** 검증 기록이 남아 있습니다.

## 3. Bedrock API 사용량 (실측)

### 3.1 개발용 — us-west-2 (Claude 계열)

멀티에이전트 개발 작업에 사용된 호출입니다.

| 모델 | 호출 수 | 입력 토큰 | 출력 토큰 | 캐시 읽기 | 캐시 쓰기 |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5 | 12,160 | 1,707,323 | 16,332,390 | 1,146,263,285 | 33,819,222 |
| Claude Sonnet 4.6 | 2,401 | 256,203 | 83,695 | 104,058,475 | 5,030,336 |
| Claude Haiku 4.5 | 95 | 209,895 | 9,633 | 63,154 | 171,418 |
| **합계** | **14,656** | **2,173,421** | **16,425,718** | **1,250,384,914** | **39,020,976** |

- 서버 오류 6건 외 실패는 없었습니다.
- 총 토큰의 대부분(약 12.5억 토큰)이 **캐시 읽기**입니다. 이는 프롬프트 캐싱이
  정상 동작하여 동일 컨텍스트를 반복 전송하지 않았음을 의미하며, 캐시 읽기 단가는
  일반 입력 단가보다 현저히 낮습니다.
- 출력 토큰 1,643만 토큰은 실제 생성된 코드·설계 문서의 분량에 해당합니다.

### 3.2 애플리케이션 런타임 — ap-northeast-2

개발이 아닌, 배포된 애플리케이션이 자체적으로 발생시킨 호출입니다.

| 모델 | 호출 수 | 입력 토큰 | 클라이언트 오류 |
| --- | --- | --- | --- |
| `amazon.titan-embed-text-v2:0` | 499,752 | 1,542,690,499 | 1,130 |
| Claude 3.5 Sonnet (3종 합계) | 4 | - | 0 |

Titan 임베딩 호출 499,752건은 **사람의 개발 행위가 아니라 배포된 분석 워커가
자동으로 발생시킨 것**입니다. 시간대별로 조회한 결과 다음 두 국면으로 명확히 나뉩니다.

**1국면 — 정상 대량 색인 (8/19 10시 ~ 8/20 08시)**
시간당 약 12,500~13,158건이 **클라이언트 오류 0건**으로 지속되었습니다.
심야 시간대에도 사람이 없는 상태에서 속도가 일정하게 유지되었으므로,
이는 사람의 조작이 아닌 **기계적 대량 색인 작업이 정상 처리된 구간**입니다.

**2국면 — 재시도 반복 (8/20 10시 ~ 8/21 11시)**
시간당 약 1,800~2,970건으로 떨어지면서 **시간당 오류가 27~33건으로 거의 일정하게**
발생하였습니다. 약 2분마다 1건씩 규칙적으로 실패하는 패턴으로,
동일한 요청이 반복 재시도되고 있었음을 나타냅니다.

원인은 분석 워커가 50,000자를 초과하는 텍스트를 Titan 임베딩 모델에 잘라내지 않고
전달한 것으로, `ValidationException: expected maxLength: 50000, actual: 52138`
오류가 재시도 루프에 들어간 것입니다. 워커 로그 활동은 2026-08-21 11:06(KST)에
멈추었습니다.

> 유의사항: 전체 499,752건이 낭비된 재시도가 아닙니다. 1국면은 정상 처리된
> 색인 작업이며, 재시도 루프에 해당하는 것은 2국면의 오류 1,130건 및 그에
> 수반된 호출입니다.

## 4. 조회 방법

| 대상 | 조회 수단 |
| --- | --- |
| 호출 수·토큰 수 | CloudWatch `AWS/Bedrock` 네임스페이스, `GetMetricData`, Period=3600, `ModelId` 차원 |
| 시간대별 패턴 | 동일 지표를 1시간 단위로 KST 기준 재집계 |
| 호출 주체 | CloudTrail `InvokeModel` 이벤트 |
| 개발 이력 | Git 커밋 로그 및 `docs/specs/track-*.md` |

전 리전(16개)을 조회하였으며, Bedrock 지표가 존재하는 리전은 **us-west-2**와
**ap-northeast-2** 두 곳뿐입니다. us-west-2에서 Opus 5는 `{ModelId}`와
`{ModelId, ContextWindow}` 두 종류의 차원 조합으로 지표가 기록되므로,
중복 집계를 피하기 위해 `ModelId` 단독 조합만 사용하였습니다.

## 5. 조회 한계 (사실 그대로 기재)

정확성을 위해 조회하지 못한 항목을 명시합니다.

1. **실제 청구 금액 미확인**
   `ce:GetCostAndUsage` 호출이 조직 SCP(`p-o83mmnhs`)에 의해 명시적으로 거부되어
   Cost Explorer 기반 실제 비용을 조회할 수 없었습니다. 본 문서의 수치는 모두
   **호출 수와 토큰 수**이며, 금액이 아닙니다.

2. **프롬프트 원문 로그 없음**
   Bedrock 모델 호출 본문 로깅(model invocation logging)이 두 리전 모두
   비활성 상태였습니다. 따라서 개별 프롬프트·응답 내용은 존재하지 않으며,
   본 문서는 집계 지표와 Git 이력만을 근거로 작성되었습니다.

3. **Titan 호출의 기간 범위**
   ap-northeast-2 Titan 지표는 8월 18일부터 기록되어 있습니다.
   8월 14~17일 구간에는 해당 호출이 존재하지 않습니다.

## 6. 결론

2026년 8월 14일부터 8월 21일까지 AWS Bedrock을 사용하여 멀티에이전트 병렬 개발을
수행하였으며, 개발 목적의 Claude 호출은 **14,656건**, 애플리케이션 런타임의
임베딩 호출은 **499,752건**이었습니다.

개발 측 호출은 레인·트랙 단위로 격리된 병렬 구조 하에서 발생한 정상 작업이며,
Git 이력상 동일 분 내 다중 커밋으로 병렬 실행이 확인됩니다.

런타임 측 호출량이 큰 이유는 사람의 개발 행위가 아니라, 배포된 분석 워커의
대량 색인 작업(정상) 및 입력 길이 초과로 인한 재시도 반복(결함)에 기인합니다.
후자는 입력 텍스트를 50,000자 이내로 잘라내는 수정이 필요한 사항으로 확인되었습니다.
