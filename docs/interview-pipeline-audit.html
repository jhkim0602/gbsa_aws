1.2 잘 되어 있는 것 (그대로 유지 권고)

근거 역추적이 구조로 강제됨

질문 하나마다 question_rationales(왜 물었는가)와 question_source_references(무엇을 근거로 물었는가)가 별도 행으로 남습니다. 리포트의 evidence는 지원자 최종 턴 ID와 자막 세그먼트, 영상 구간을 모두 가리켜야만 CONFIRMED가 됩니다. 검증 실패 시 조용히 통과하지 않고 INSUFFICIENT_EVIDENCE로 떨어집니다.

환각 출처를 코드가 잘라냄

질문 생성 모델이 반환한 출처 ID 중 그 턴에서 실제로 검색된 ID 집합에 없는 것은 버립니다 (interview_service.py의 retrieved_by_id 필터). 모델이 그럴듯한 출처를 만들어내도 저장되지 않습니다. 감리에서 가장 높게 평가하는 지점입니다.

멱등성이 데이터베이스에 있음

웹소켓 명령은 interview_command_results에 (company_id, session_id, operation, idempotency_key) 복합 PK로 결과를 저장합니다. 네트워크가 끊겨 같은 answer.complete가 두 번 와도 턴은 하나만 생깁니다. 메모리 캐시가 아니라 durable 저장이라 프로세스 재시작에도 유지됩니다.

테넌시가 SQL 레이어에 있음

테넌트 분리를 API 검증에만 의존하지 않고 리포지토리 쿼리의 WHERE company_id로 강제합니다. 다른 회사 객체를 조회하면 403이 아니라 404가 나오므로 존재 여부조차 노출되지 않습니다.

기준은 하나입니다. npm 스크립트나 pytest 한 줄로 똑같이 표현할 수 없는 것만 남겼습니다. Makefile 첫 줄에 그 기준을 주석으로 적어 뒀습니다.

3.1 왜 모놀리식인가 — 감리 판단

레인을 4개로 나눴으면서도 서비스를 4개로 쪼개지 않은 것은 합리적인 선택으로 봅니다. 근거는 실시간 경로입니다. 면접 1턴은 음성 인식 → 검색 → 질문 생성 → 정책 검사 → 저장을 지원자가 기다리는 동안 끝내야 하는데, 이 과정이 Lane B(검색)와 Lane C(면접)에 걸쳐 있습니다. 서비스가 분리돼 있었다면 이 구간에 네트워크 왕복이 최소 2회 추가됩니다. 대신 경계는 make boundaries-check로 기계적으로 강제해 두었습니다 — 나중에 정말 쪼개야 할 때 쪼갤 수 있는 상태를 유지하는 구조입니다.

3.2 아웃박스가 하는 일

이벤트를 큐에 직접 넣지 않고 업무 데이터와 같은 트랜잭션으로 outbox_events 테이블에 먼저 씁니다. 이 한 가지 선택이 두 종류의 사고를 동시에 막습니다.

4.3 사람 검토가 AI 원본을 덮어쓰지 않는 구조

이 부분은 별도로 확인했습니다. reports에는 kind 컬럼이 있고 워커는 항상 AI_ORIGINAL로 씁니다. 사람의 수정은 reports를 UPDATE하지 않고 human_reviews에 새 행을 추가합니다(review_type, target_id, value JSON, reason, company_user_id).

감리 의견

6.1 업로드가 2단계인 이유

파일을 API로 바로 올리지 않고 upload-intents로 의도를 먼저 등록한 뒤 브라우저가 객체 저장소로 직접 올립니다. 이유가 세 가지입니다.

  • API 프로세스가 파일 본문을 만지지 않습니다. 100MB 이력서가 실시간 면접 프로세스의 메모리를 잡아먹는 사고가 구조적으로 불가능합니다.

  • 서명 URL에 만료가 있습니다. expires_at이 지나면 그 URL로는 올릴 수 없습니다.

6.2 이 단계에서 확정되는 것 — 꼬리질문 한도

감리에서 가장 눈여겨본 부분입니다. 꼬리질문을 몇 번까지 할지가 면접 전에 정수로 확정됩니다.

verification_targets  (분석 워커가 면접 전에 생성)

  ├ target_type               ← 왜 확인이 필요한가 (5종)
  ├ objective (4000자)        ← 무엇을 확인해야 하는가
  ├ priority                  ← 몇 번째로 물을 것인가
  └ max_follow_ups            ← 꼬리질문 상한. 면접 중에 바뀌지 않음

candidate_verification_maps  (타깃들의 순서와 예산)
  ├ ordered_target_ids JSON    ← 정렬된 타깃 ID 목록

감리 의견 — "AI가 알아서 물어본다"가 아닙니다

면접 중 AI의 자유도는 질문 문장을 만드는 것으로 제한됩니다. 무엇을 물을지(objective), 몇 번 물을지(max_follow_ups), 어떤 순서로 물을지(ordered_target_ids)는 면접 전에 결정됩니다. 이는 두 가지를 보장합니다 — ① 면접 시간이 예측 가능하고, ② 같은 기준으로 지원한 사람들이 같은 범위의 검증을 받습니다. 모델이 그날 기분에 따라 어떤 지원자에게는 5번 캐묻고 다른 지원자에게는 1번만 묻는 일이 발생하지 않습니다.

하이브리드 검색(RAG)

"레드 검색"으로 물어보신 부분입니다. 벡터 검색만 쓰지 않고 세 가지 점수를 가중 합산합니다.

7.1 왜 벡터 검색만으로는 안 되는가

검색 방식잘하는 것못하는 것 — 면접에서의 실패
벡터만 (× 0.55) "동시성 처리 경험" → "락 경합을 줄였다" 같은 표현이 달라도 의미가 같은 문서를 찾음 UserRepository를 물었는데 의미상 비슷한 OrderRepository를 가져옴 → 면접관이 존재하지 않는 코드를 근거로 질문
어휘만 (× 0.30) 단어가 실제로 문서에 있는지 확인 한국어에서 조사·어미 때문에 신뢰도가 낮음. "구현했습니다"와 "구현"이 다른 토큰
심볼 완전일치 (× 0.80) 함수·클래스명 직격. lower(symbol) = lower(:query) 이름을 정확히 모르면 무용지물
가중치 0.80 > 0.55의 의미 — 감리 해석

심볼 완전일치가 벡터 유사도보다 높은 가중치를 받습니다. 코드 면접에서는 "정확히 그 코드"가 아니면 질문이 성립하지 않기 때문입니다. 비슷한 코드를 근거로 질문하면 지원자는 "저는 그런 코드를 쓴 적이 없습니다"라고 답할 수밖에 없고, 그 순간 면접 전체의 신뢰가 무너집니다.

반대로 어휘 점수를 0.30으로 낮게 둔 것은 한국어 형태소 분석기 없이 'simple' 설정을 쓰기 때문입니다. to_tsvector('simple', …)은 한국어를 공백으로만 자릅니다. 이 한계를 알고 가중치를 낮춘 것으로 보이며, 감리에서 솔직한 설계로 평가합니다 — 한국어 검색 품질을 과장하지 않았습니다.

validate_timeline은 영상 구간이 자기 자막 세그먼트 안에 들어있는지를 봅니다. 그런데 그 자막 세그먼트의 시각도 같은 잘못된 값에서 왔습니다. 잘못된 기준에 대해 일관되므로 검증을 통과합니다. 결과적으로 CONFIRMED가 붙은 Evidence가 엉뚱한 시각을 가리킬 수 있습니다.

이것이 F-02(재생 불가)보다 무거운 이유는, 재생이 안 되는 것은 보이는 고장이지만 이것은 재생이 붙는 순간 조용히 틀린 장면을 보여주는 것이기 때문입니다. 검토자는 "AI가 근거로 든 발언"을 확인하려고 그 시각으로 이동했는데 다른 발언을 듣게 됩니다.

고칠 데이터는 이미 저장되어 있습니다

추가 수집이 필요한 문제가 아닙니다. 클라이언트는 답변을 확정할 때마다 last_recording_chunk_sequence를 함께 보내고(api/live_handlers.py:283), 서버는 그것을 session_checkpoints에 (last_final_turn_id, last_media_chunk_sequence) 쌍으로 기록합니다 (interview_service.py:265-272 · 398-405 · 463-470). 즉 어느 턴이 어느 청크 번호까지 진행했는지가 이미 durable하게 남아 있습니다.

권고: 미디어 워커가 chunks[index] 대신 이 체크포인트 쌍으로 턴 경계를 복원하도록 바꿉니다 (현재 runtime/worker.py와 integration/interview_reporting.py에 checkpoint 참조가 0건입니다). 더 견고하게 하려면 interview_turns에 session_start_ms/session_end_ms를 직접 두는 편이 낫습니다 — 현재 이 테이블에는 시각 컬럼이 하나도 없어 시간 기준 조인 자체가 불가능하고, 그래서 위치 짝짓기가 나온 것으로 보입니다.

영상은 어떻게 들어가는가

물어보신 부분입니다. 결론: 영상 "분석"은 존재하지 않습니다. 영상은 무결성 증명과 근거 고정에만 쓰입니다.

11.1 없다는 것을 어떻게 확인했는가

추측이 아니라 전수 검색으로 확인했습니다. 저장소 전체에서 다음 7개 키워드의 검색 결과가 0건입니다.

11.2 그러면 영상은 무엇을 하는가

① 무결성 — 편집되지 않았음의 증명

청크마다 SHA-256과 순번과 시각 구간이 남습니다. 미디어 워커가 이를 정렬하며 겹침·역순을 예외로 처리하고, 빈 구간은 missing_ranges에 기록합니다. 최종 자산 해시는 청크 해시들을 순서대로 이어붙인 sha256이므로 한 청크만 바뀌어도 전체 해시가 달라집니다.

② 근거 고정 — 구조는 갖췄지만 시각이 어긋납니다

리포트의 각 evidence 행이 answer_turn_id + transcript_segment_id + video_start_ms/video_end_ms를 동시에 가리킵니다. 구조적으로는 몇 분 몇 초의 그 발언으로 되돌아갈 수 있게 설계됐고, 구간 검증에 실패하면 CONFIRMED가 되지 않습니다. 다만 그 시각을 정하는 지점이 턴을 청크와 위치로 짝짓고 있어(F-09) 현재 값은 두 번째 턴부터 실제 발언 시각과 다릅니다. 턴 ID와 자막 연결은 맞으므로 어느 발언인지는 특정되지만, 영상에서 몇 초인지는 아직 신뢰할 수 없습니다.

감리 의견 — 이것은 미구현이 아니라 설계 선택으로 봅니다

근거가 셋입니다.

  • Evidence 구조가 그것을 허용하지 않습니다. evidence는 반드시 answer_turn_id(지원자의 최종 답변 턴)를 가리켜야 합니다. "표정이 불안해 보였다"는 관찰은 어떤 답변 턴에도 연결되지 않으므로 이 구조에 들어갈 자리가 없습니다.
  • 검증 타깃 5종이 모두 말한 내용에 관한 것입니다. 모순·미언급·소유권·누락 차원·주장 — 겉모습에 관한 유형이 하나도 없습니다.
  • 영상 처리 파이프라인이 프레임을 열지 않습니다. 미디어 워커는 청크를 바이트와 해시와 시각으로만 다룹니다. 디코딩 자체가 없습니다.

표정·시선·자세로 사람을 평가하는 기능은 여러 나라에서 법적·윤리적 문제가 제기되는 영역입니다. 그것을 구현했다가 끄는 것과 애초에 들어갈 자리를 만들지 않는 것은 다릅니다. 후자입니다.

감리 총평

이 시스템의 핵심 주장은 "AI가 만든 모든 판단은 지원자의 실제 답변으로 되돌아갈 수 있다"입니다. 감리 결과, 그 주장을 뒷받침하는 구조는 실제로 구현되어 있습니다.

  • evidence가 답변 턴 ID · 자막 세그먼트 ID · 영상 구간을 동시에 요구하고, 검증 실패 시 CONFIRMED가 되지 않습니다 (단 그 영상 시각 값은 F-09로 아직 틀립니다)
  • 질문의 근거가 question_source_references로 별도 기록되고, 모델이 만들어낸 가짜 출처는 코드가 잘라냅니다
  • 기준 버전 ID가 초대→전략→세션→리포트에 동일하게 박혀 평가 기준의 사후 변경을 무력화합니다
  • 사람의 수정이 AI 원본을 덮어쓰지 않고 human_reviews에 누적됩니다
  • 영상은 판단의 입력이 아니라 검증 수단으로만 쓰입니다

비어 있는 것은 대부분 그 구조 안에 들어갈 내용입니다. Evidence를 검증하는 코드는 동작하는데 Evidence에 붙일 관찰 문장을 모델이 쓰지 않고, 영상 구간을 재생할 자산이 만들어지지 않습니다.

순서로서는 옳습니다. 근거 검증 골격 없이 모델을 먼저 붙였다면 그럴듯한 문장이 근거 없이 저장되는 시스템이 됐을 것이고, 나중에 근거를 강제하려면 전체를 다시 만들어야 했을 것입니다. 지금은 모델을 붙이면 그 출력이 자동으로 근거 검증을 받는 상태입니다.

단 하나, 위 주장을 실제로 깨는 항목이 F-09입니다. "실제 답변으로 되돌아갈 수 있다"의 마지막 한 걸음(영상에서 몇 초인지)이 턴을 청크와 위치로 짝지어 정해지고 있고, 검증조차 그 잘못된 값을 기준으로 삼아 통과시킵니다. 구조가 옳기 때문에 고칠 범위는 좁습니다 — 필요한 데이터(session_checkpoints의 턴↔청크 번호 쌍)는 이미 저장되어 있고, 미디어 워커가 그것을 읽기만 하면 됩니다. F-08도 같은 성격(조용한 오류)이므로 두 항목을 함께 닫는 것을 권고합니다.
