
`.env`에 **아래 두 값을 추가**하세요. 없으면 API가 기동하지 않습니다 (병합으로 capacity 큐가 필수가 됨).

```

LOCAL_CAPACITY_QUEUE_NAME=iep-capacity
```

`.env.example`은 생성/임베딩 제공자를 `gcp`(Gemini)로 권하지만 **코드 기본값은 `aws`** 입니다.

임베딩 제공자를 바꾸면 기존에 색인된 문서는 다시 분석해야 검색이 맞습니다.

## 무엇이 문제였고 어떻게 고쳤는지

### 1. 면접이 끝나도 지원자 상태가 그대로였다

지원자 관리의 "검토 대기"는 `invitation.status == "completed"`, "검토 완료"는 `reviewed`를 셉니다.
그런데 그 두 상태로 **전이시키는 코드가 없었습니다**. 면접을 몇 번 돌려도 카운터가 0이었습니다.

- 면접 완료 → `interview.completed` 핸들러가 `ready → interviewing → completed` 전이
  (`runtime/worker.py`). 도메인이 그 경로만 허용하고 면접 시작 이벤트가 없어 `interviewing`을 통과시킵니다.
- 최종 결정 기록 → `completed → reviewed` 전이 (`reporting/application/review_service.py`).
  결정을 **먼저 저장한 뒤** 전이하고, 전이 실패는 예외로 올리지 않습니다.

### 2. 분석이 끝나도 `materials_submitted`에서 멈췄다

`AnalysisRequestedEventHandler`는 전이 권한을 **가장 작은 `submission_id`** 에게만 줍니다.
그런데 invitation은 마지막 필수 자료가 들어온 뒤에야 `materials_submitted`가 되므로,
권한을 가진 제출물의 분석 이벤트는 **그보다 이르고** 시점이 맞는 제출물은 **권한이 없습니다.**
아무도 전이하지 못해 `ready`에 도달할 수 없었습니다.

→ `AnalysisCompletedEventHandler`가 `materials_submitted`를 발견하면 직접
`analyzing`을 거쳐 `ready`까지 보냅니다. 기존 `min` 조건과 그 테스트는 그대로 두었습니다.

### 3. 로컬 큐가 30초 만에 메시지를 회수했다

`local_infra`가 큐를 속성 없이 만들어 SQS 기본값 **30초**가 됐는데, 런타임은 300초를 가정해
heartbeat를 100초마다 보냅니다. 리포트 생성이 30초를 넘기면 메시지가 재배달되어
**다른 워커가 같은 작업을 반복**했고 `uq_report_session_version` / `uq_submission_analyses_version`
위반이 떴습니다. DLQ도 없어서 실패한 메시지는 흔적 없이 사라졌습니다.

→ `runtime/queue_topology.py`를 두어 큐를 만드는 쪽과 소비하는 쪽이 같은 값을 읽습니다.
값은 `infra/modules/async-workflow/main.tf`와 일치하고, 테스트가 그 일치를 검사합니다.
DLQ도 함께 생성합니다.

### 4. 리포트가 생성되지 않았다 (outbox head-of-line blocking)

`interview.checkpoint_changed`는 outbox에 쓰이지만 라우팅 대상이 아니어서 **영구히 pending으로
누적**됩니다(면접 1회당 약 45건). dispatcher는 오래된 순으로 100건만 읽으므로, 이것이 100건을
넘긴 뒤에는 뒤에 있는 `interview.completed`가 **영원히 보이지 않았습니다.**

→ dispatcher가 자기가 라우팅할 수 있는 타입만 조회합니다. 필터는 **limit보다 먼저** 적용됩니다.

### 5. 검토 결과가 조용히 사라졌다

- 평가 수정이 `await` 없이 호출되고 바로 성공 문구를 띄웠습니다. 서버가 거절해도 "기록했습니다".
- 최종 결정 버튼은 `catch`가 없어 **실패 시 화면에 아무 변화도 없었습니다.** 반응이 없어 다시
  누르면 중복 기록됐습니다.
- 검토 이력은 `history` prop을 아무도 넘기지 않아 **항상 비어 있었습니다.**
- 서버가 `value`/`reason`을 반환하지 않아, 이력에 "무슨 결정"인지 표시할 수 없었습니다.

→ 쓰기 경로에 await·catch·pending을 넣고, 서버 에러 사유를 화면에 노출합니다.
`HumanReviewView`에 `value`/`reason`을 추가해(계약 3곳 함께 수정) 이력에 결정과 사유가 보입니다.

### 6. 그 밖의 프론트 문제

- **제출 상태**: 입력을 한 글자 고치면 서버에서 받아온 "제출 완료"가 "미제출"로 돌아갔습니다.
  이제 편집은 **실패만** 지웁니다. 제출한 저장소 URL도 복원됩니다(서버가 이미 주고 있었습니다).
- **멱등키**: 매 호출 랜덤 UUID여서 버튼 두 번 클릭이 두 건으로 저장됐습니다(실제로 자기소개서가
  2초 간격으로 2건 들어왔습니다). 파일 해시·URL 기반 안정 키로 바꿨습니다.
- **초대 발송**: `rejectedCount`가 화면에 없어서 0명 발송도 성공 배너였습니다. 이제 실패 건수를
  표시합니다. 부수적으로 `loadInvitations()`가 방금 쓴 메시지를 지우는 버그도 고쳤습니다.
- 면접 시작 직후 세션이 `preparing`에 갇히던 회귀도 고쳤습니다 (커밋 `cd8ddc8`).

## 알아두면 좋은 것

- **워커를 재시작할 때는 PowerShell 창에서 Ctrl+C로 종료하세요.** 프로세스를 강제 종료하면
  `run_workers.py`가 띄운 자식 워커가 고아로 남아 **옛 코드로 큐를 계속 소비합니다.**
  이 때문에 고친 코드가 반영되지 않은 것처럼 보이는 일이 있었습니다.
- 상태 라벨은 `completed` = **"검토 대기"**, `reviewed` = **"검토 완료"** 입니다.
  "면접 완료"라는 라벨은 없습니다.
- **면접 진행 중 상태는 화면에 거의 보이지 않습니다.** 면접 시작 이벤트가 없어 완료 시점에
  `interviewing`을 통과하기 때문입니다. 필요하면 면접 시작 전이를 추가해야 합니다.
