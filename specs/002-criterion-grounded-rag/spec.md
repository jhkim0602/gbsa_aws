# Feature Specification: Criterion-Grounded Interview RAG

**Feature Branch**: `not-created`

**Created**: 2026-08-15

**Status**: Approved

**Input**: User description: "기업이 손쉽게 직무 요구사항과 평가기준을 설정하고, 기업 기준과 지원자 자료를 함께 검색해 누락·충돌·불확실성을 검증하는 질문을 생성한다. AI 면접관 설정은 제거하고 Aurora PostgreSQL 기반 하이브리드 검색으로 전환한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채용 기준을 쉽게 게시 (Priority: P1)

채용담당자는 채용공고와 역할 설명을 바탕으로 필수·우대 요구사항과 5~8개의 평가기준을
쉽게 작성하고, 실제 답변에서 확인할 요소와 질문 방향을 검토한 뒤 버전으로 게시한다.

**Why this priority**: 게시된 기업 기준이 검색, 질문과 평가의 고정 축이므로 다른 모든
흐름보다 먼저 정확하고 사용하기 쉽게 정의돼야 한다.

**Independent Test**: 한 포지션에서 여러 필수·우대 기준을 작성하고 게시한 뒤 각 기준의
가중치, 관찰 요소, 질문과 판단 유보 원칙이 같은 불변 버전으로 조회되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 채용공고와 역할 설명이 있을 때, **When** 담당자가 기준을 작성하면,
   **Then** 필수·우대 구분, 중요도, 확인할 행동, 좋은 답변 요소, 추가 확인 조건과
   기본 질문을 기준별로 저장할 수 있다.
2. **Given** 여러 기준의 중요도가 설정됐을 때, **When** 게시를 시도하면, **Then**
   시스템은 유효한 기준과 가중치를 검증하고 불변 버전을 생성한다.
3. **Given** 민감하거나 직무와 무관한 요구사항이 있을 때, **When** 게시를 시도하면,
   **Then** 시스템은 해당 내용을 차단하고 수정 이유를 표시한다.
4. **Given** 채용 설정 화면을 사용할 때, **When** 담당자가 면접 운영을 구성하면,
   **Then** 면접관 이름·성격·음성 선택 없이 시간과 금지 주제만 결정한다.

### User Story 2 - 기업 기준과 지원자 자료의 검증 지도 생성 (Priority: P1)

시스템은 게시된 기업 기준과 지원자 자료를 함께 검색해 기준별 관련 주장, 누락된 세부
내용, 자료 간 충돌과 코드 기여 불확실성을 지원자별 검증 지도로 만든다.

**Why this priority**: 관련 문서를 찾는 것만으로는 직무 적합성 검증 질문을 만들 수 없고,
기업 기준 대비 무엇을 확인해야 하는지 명시해야 한다.

**Independent Test**: 고정된 기업 기준과 자료 묶음을 입력하고 기준별 주장·누락·충돌과
원문 위치가 예상 검증 지도와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** "ECS 운영 장애 대응 경험 우대" 기준과 ECS 배포만 언급한 자료가 있을 때,
   **When** 분석이 완료되면, **Then** ECS 경험 언급과 장애 원인·복구 역할·재발 방지
   미확인을 구분한다.
2. **Given** 이력서와 포트폴리오의 역할 또는 기간이 다를 때, **When** 분석이 완료되면,
   **Then** 양쪽 원문 위치와 중립적인 확인 목적을 연결하고 허위로 단정하지 않는다.
3. **Given** 저장소의 관련 코드에 지원자 기여 범위가 불확실할 때, **When** 분석이
   완료되면, **Then** 전체 저장소를 지원자 소유로 간주하지 않고 직접 수행 범위를
   확인할 대상으로 만든다.
4. **Given** 기준 관련 자료가 없을 때, **When** 분석이 완료되면, **Then** 부적합으로
   평가하지 않고 자료 미언급 상태와 공통 질문을 준비한다.

### User Story 3 - 검증 목적에 맞는 질문과 꼬리질문 진행 (Priority: P1)

지원자는 동일한 기업 평가축 안에서 자신의 자료에 있는 주장, 누락과 충돌 후보를
확인하는 중립적 질문을 받고 실제 경험과 본인 역할을 설명한다.

**Why this priority**: 기업 기준과 자료 분석을 실제 답변 Evidence로 연결하는 핵심
사용자 가치다.

**Independent Test**: 검증 지도가 준비된 세션에서 최초 질문, 최종 답변, 꼬리질문과
다음 기준 이동을 실행하고 질문마다 하나의 기준과 검증 목적만 존재하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 장애 대응 내용이 미확인일 때, **When** 질문을 생성하면, **Then** 실제
   장애 사례, 원인 분석, 복구 과정과 본인 역할을 확인하는 하나의 질문을 제시한다.
2. **Given** 답변에 본인 역할이 빠졌을 때, **When** 답변이 확정되면, **Then** 같은
   기준에서 직접 수행한 행동만 확인하는 짧은 꼬리질문을 제시한다.
3. **Given** 검증 목표가 충분히 답변됐을 때, **When** 다음 질문을 선택하면, **Then**
   반복하지 않고 아직 확인되지 않은 우선순위 기준으로 이동한다.
4. **Given** 검색 기능이 제한됐을 때, **When** 다음 질문이 필요하면, **Then** 공통
   질문으로 진행하고 제한 모드를 기록한다.

### User Story 4 - 질문 근거와 실제 Evidence를 검토 (Priority: P2)

기업 검토자는 각 질문의 기업 기준, 검증 목적과 참조 자료 원문을 확인하고, 지원자
자료와 실제 답변 Evidence를 명확히 구분한다.

**Why this priority**: 개인화 질문의 이유를 사람이 검토할 수 있어야 신뢰성과 책임성을
확보할 수 있다.

**Independent Test**: 완료된 질문을 선택해 기준, 검증 목적, 자료 원문, 검색·생성
버전과 실제 답변 Evidence를 각각 확인한다.

**Acceptance Scenarios**:

1. **Given** 자료 기반 질문이 있을 때, **When** 질문 근거를 열면, **Then** 대상 기준,
   확인하려던 누락·충돌 항목과 원문 위치가 표시된다.
2. **Given** 지원자가 답변했을 때, **When** 리포트를 검토하면, **Then** 자료는
   Source Reference로, 최종 답변·자막·영상은 Evidence로 분리된다.
3. **Given** 자료와 답변이 다를 때, **When** 결과가 생성되면, **Then** 거짓이나
   과장을 자동 판정하지 않고 불확실성과 사람 검토 필요성을 표시한다.

### Edge Cases

- 하나의 자료 구절이 여러 기준과 관련돼도 기준별 검증 목적을 독립적으로 유지한다.
- 자료 반복 횟수와 문서 완성도를 사실성이나 역량 점수로 사용하지 않는다.
- 추상적인 기업 기준은 게시 전에 관찰 가능한 요소 보완을 요구한다.
- 지원자가 자료에 없던 경험을 답변해도 불이익을 주지 않는다.
- 시간이 부족하면 필수 기준과 근거 부족 기준을 우선하고 나머지는 미확인으로 남긴다.
- 질문이 비난, 유도, 복수 질문 또는 금지 주제를 포함하면 공통 질문으로 대체한다.
- 임베딩 또는 전문검색 한쪽이 실패하면 가능한 검색 방식으로 제한 운영한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 기업은 포지션별 필수·우대 요구사항과 중요도를 정의할 수 있어야 한다.
- **FR-002**: 기업은 1개 이상의 평가기준을 작성하고 각 기준을 요구사항과 연결할 수 있어야 한다.
- **FR-003**: 각 기준은 설명, 가중치, 확인할 요소, 좋은 답변 요소, 추가 확인 조건,
  판단 유보 지침, 공통 질문과 꼬리질문 방향을 포함해야 한다.
- **FR-004**: 기업 설정 UI는 AI 면접관 이름, 외형, 성격, 말투 또는 음성을 요구하지 않아야 한다.
- **FR-005**: 게시된 요구사항과 평가기준은 불변 버전이며 기존 초대와 세션에 유지돼야 한다.
- **FR-006**: 시스템은 금지 주제, 보호 특성, 직무와 무관한 개인정보와 자동 탈락 조건을 차단해야 한다.
- **FR-007**: 시스템은 유효한 동의가 있는 자료만 분석·검색해야 한다.
- **FR-008**: 기업 요구사항, 평가기준 가이드와 지원자 자료는 승인된 의미 임베딩과
  전문검색 표현을 가질 수 있어야 한다.
- **FR-009**: 검색은 기업, 지원자, 초대, 기준 버전을 강제하고 다른 범위의 자료를 반환하지 않아야 한다.
- **FR-010**: 검색은 의미 유사도, 키워드, 정확한 기술·심볼, 자료 유형과 제한된 기여
  신뢰도를 결합해야 한다.
- **FR-011**: 시스템은 자료에서 경험, 역할, 기술 선택, 결과와 기여 범위 주장 후보를
  추출하고 재현 가능한 원문 위치에 연결해야 한다.
- **FR-012**: 자료 주장은 사실이나 Evidence로 확정되지 않아야 한다.
- **FR-013**: 시스템은 기준별 관련 주장 없음, 관련 주장 있음, 세부 내용 부족, 자료
  충돌과 기여 불확실성을 구분해야 한다.
- **FR-014**: 시스템은 기준, 주장, 누락, 충돌, 질문 목적, 우선순위와 Source Reference를
  포함한 지원자별 검증 지도를 생성해야 한다.
- **FR-015**: 검증 지도는 기준·자료 분석·임베딩·검색·생성 버전을 포함해야 한다.
- **FR-016**: 다음 검증 목표는 필수 여부, 중요도, 근거 부족, 이전 답변과 남은 시간을
  고려해 선택돼야 한다.
- **FR-017**: 하나의 질문은 하나의 평가기준과 하나의 검증 목적만 대상으로 해야 한다.
- **FR-018**: 질문 모델에는 기준 원문, 관찰 지침, 관련 자료 원문, 최근 최종 답변,
  미확인 요소와 금지 주제가 전달돼야 한다.
- **FR-019**: 자료 누락을 경험 부재로, 충돌을 허위로, 저장소 전체를 지원자 소유로
  단정하지 않는 중립적인 질문을 생성해야 한다.
- **FR-020**: 최종 답변이 부족하면 같은 기준에서 하나의 구체적인 꼬리질문을 선택해야 한다.
- **FR-021**: 목표가 충분히 다뤄지면 다음 우선순위 목표로 이동해야 한다.
- **FR-022**: 검색·생성 실패 시 공통 질문으로 진행하고 제한 모드를 기록해야 한다.
- **FR-023**: 질문마다 기준 버전, 검증 목적, Source Reference, 검색·생성 버전과 정책
  결과를 저장해야 한다.
- **FR-024**: 자료와 검색 결과는 Source Reference로만 사용하고 Evidence가 되지 않아야 한다.
- **FR-025**: 확인 또는 부분 확인 상태는 실제 최종 답변 Evidence가 있을 때만 허용돼야 한다.
- **FR-026**: 시스템은 자료와 답변의 차이를 거짓, 과장 또는 부정행위로 자동 판정하지 않아야 한다.
- **FR-027**: 검토자는 질문 근거, 자료 원문과 실제 Evidence를 분리해 볼 수 있어야 한다.
- **FR-028**: 원본, 임베딩, 전문검색 표현, 주장, 검증 지도와 질문 참조는 보관 만료와
  삭제 요청에 함께 삭제되고 부재가 검증돼야 한다.
- **FR-029**: 원문, 답변, 임시 접근 주소와 임베딩 입력은 운영 로그에 기록되지 않아야 한다.
- **FR-030**: 고정 회귀 자료로 검색, 검증 지도, 질문, Evidence 분리와 삭제를 반복 검증해야 한다.

### Key Entities

- **JobRequirement**: 필수·우대 구분, 중요도와 연결 기준을 가진 기업 요구사항이다.
- **CriterionVerificationGuide**: 기준별 관찰 요소, 좋은·부족한 답변 지침과 질문 방향이다.
- **RetrievalDocument**: 기업 기준 또는 지원자 자료의 보호된 원문과 버전 있는 검색 표현이다.
- **CandidateClaim**: 자료에서 추출한 주장 후보와 출처이며 사실이나 Evidence가 아니다.
- **ClaimConflict**: 자료 사이의 확인이 필요한 차이와 양쪽 출처다.
- **VerificationTarget**: 하나의 기준에서 확인할 주장, 누락, 충돌 또는 기여 불확실성이다.
- **CandidateVerificationMap**: 지원자의 모든 검증 목표를 고정한 면접 준비 스냅샷이다.
- **QuestionRationale**: 질문의 기준, 검증 목적, 질문 유형, 정책과 Source Reference 기록이다.
- **VerificationProgress**: 실제 답변으로 다룬 목표와 미확인 목표를 나타내는 세션 상태다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신규 채용담당자가 30분 안에 포지션과 5개 이상의 기준을 게시할 수 있다.
- **SC-002**: 고정 회귀 사례의 95% 이상에서 질문이 하나의 기준과 검증 목적에 연결된다.
- **SC-003**: 자료 기반 질문의 95% 이상에서 참조 원문 위치를 다시 열 수 있다.
- **SC-004**: 누락 회귀 사례의 90% 이상에서 누락 요소를 직접 확인하는 질문이 생성된다.
- **SC-005**: 충돌 회귀 사례의 100%에서 허위를 전제하지 않는 질문이 생성된다.
- **SC-006**: 파일럿 검토자의 85% 이상이 질문을 직무 요구사항과 관련 있다고 평가한다.
- **SC-007**: 완료 면접의 90% 이상에서 모든 필수 기준에 Evidence 또는 미확인 상태가 존재한다.
- **SC-008**: 자료만으로 확인 또는 부분 확인 상태가 저장되는 사례가 0건이다.
- **SC-009**: 다른 기업·지원자의 기준, 자료 또는 검증 지도가 반환되는 사례가 0건이다.
- **SC-010**: 삭제 완료의 100%에서 모든 검색·검증 파생 표현의 부재가 확인된다.
- **SC-011**: 파일럿 규모에서 검색 결과의 95%가 사용자가 인지할 수 있는 시간 안에 표시된다.
- **SC-012**: OpenSearch 없이 전체 제출-면접-검토 흐름이 성공한다.

## Assumptions

- 1차 범위는 한국어 IT·개발 직군과 공개 저장소다.
- 기업 기준은 지원자마다 변하지 않고 질문과 순서만 개인화된다.
- 채용공고 기반 기준 초안은 사람이 검토하고 게시해야 효력이 생긴다.
- 자료 미언급은 감점 근거가 아니며 답변으로 새로운 경험을 설명할 수 있다.
- 최종 평가와 채용 판단은 기존 Evidence 및 사람 검토 정책을 따른다.
- 비공개 저장소, 외부 신원 조사, 허위 자동 판정과 자동 탈락은 제외한다.
